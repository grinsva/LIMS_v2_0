# Формат проекта IntraSCADA

## Расположение

```text
C:\Program Files\IntraSCADA\                     установка, log\ih.log
C:\ProgramData\IntraSCADA\intrascada\projects\   проекты
    <PROJECT>\                                   корень проекта
```

Пример ниже — из проекта, на котором собирался скилл; в другом проекте числа и имена будут свои.
Имя проекта задаётся при запуске службы и попадает в лог:

```text
17.11 13:53:14.772 INFO: Project folder: C:\ProgramData\IntraSCADA\intrascada\projects\<PROJECT>
17.11 13:53:26.016 INFO: Device engine has started, devices: <N>
```

## Два вида хранения

### 1. Визуальные сущности — отдельные JSON-файлы

`jbase\container\vc096.json`, `jbase\layout\l010.json`,
`jbase\template\vt105.json`, `jbase\dialog\di0039.json`.

- Одна сущность = один файл, содержимое — **одна строка минифицированного JSON**.
- Кодировка UTF-8 без BOM, переводы строк не важны.
- Имя файла = `_id` сущности (регистр важен: `vc096`, не `VC096`).
- Вложенные контейнеры: `u5e34@vc010.json` — контейнер, привязанный к
  экземпляру шаблона (`u5e34@` — префикс экземпляра).

### 2. Данные и индексы — `jbase\*.db`

Формат — **JSON Lines**: один JSON-объект на строку, UTF-8, без обёртки-массива.
Читать построчно, пропуская пустые строки и (на всякий случай) битые строки.

| Файл | Назначение | Ключевые поля |
|---|---|---|
| `devices.db` | устройства | `_id` (`d0834`), `type` (`t045`), `dn`, `name`, `tags`, `parent` (`dg174`), `order`, `props` |
| `lists.db` | дерево папок устройств | `_id` (`dg172`), `parent`, `order`, `name`, `list: "place"` |
| `types.db` | типы устройств | `_id` (`t045`), `name`, `props{...}`, `alerts{...}`, `tags` |
| `devparam.db` | параметры устройств | значения/настройки по устройству |
| `devhard.db` | привязка к каналам | `did`, `prop`, `unit`, `address`, `vartype`, `dn` |
| `units.db` | модули/units | `modbus1`, `modbus3`, `opcuaserver1` и т. п. |
| `locals.db` | локальные переменные | `local063`, `local002`, ... |
| `visconts.db` | индекс контейнеров | `_id` (`vc096`), `name`, `parent` (`vcg005`), `order`, `miss` |
| `layouts.db` | индекс раскладок | `_id` (`l010`), `name`, `parent` (`lg002`) |
| `vistemplates.db` | индекс шаблонов | `_id` (`vt105`), `name` |
| `dialogs.db` | индекс диалогов | `_id` (`di0039`), `name` |
| `charts.db`, `reports.db`, `journals.db` | графики, отчёты, журналы | — |

Индекс (`visconts.db` и т. п.) хранит имя и место в дереве, а **тело** сущности
лежит в JSON-файле. Для поиска по имени удобно сначала смотреть индекс.

## Что перезаписывает служба

Наблюдение на живом проекте (18.11.2026): служба периодически пишет `*.db`
(`devcurrent.db`, `alerts.db`, `devices.db` и др.), но **не перезаписывает**
`jbase\container\*.json`, `layout\*.json`, `template\*.json`.

Практические выводы:

- JSON-сущности можно готовить и класть рядом с живыми — служба их не затрёт.
- `.db` — живые данные; правка на работающей службе бессмысленна и опасна.
- Факт перезаписи проверяется по `LastWriteTime`:

```powershell
Get-ChildItem "<проект>\jbase" -Recurse -File -Filter *.json |
  Where-Object { $_.LastWriteTime -gt (Get-Date).AddHours(-2) }
```

## Память и перезапуск

Служба загружает проект в память при старте. Если изменить `vcXXX.json` позже,
веб-клиент продолжит отдавать старую версию: контейнер берётся из памяти
процесса, а не с диска.

Признаки и проверки:

- В `ih.log` — время `Project folder` и `Device engine has started`.
- Процессы `intrascada` имеют `StartTime` раньше времени правки файла:

```powershell
Get-Process intrascada | Select-Object Id, StartTime | Sort-Object StartTime
```

Вывод: любая правка JSON применяется только после перезапуска проекта/службы.
Перезапуск выполняет владелец; агент его не делает.

## Кодировка и типичные проблемы

- Читать/писать только UTF-8. PowerShell 5 по умолчанию может добавить BOM —
  использовать `[IO.File]::WriteAllText($p, $s, [Text.UTF8Encoding]::new($false))`
  или Node.js `fs.writeFileSync(p, s, 'utf8')`.
- Консоль Windows может показывать русский текст как `�����` — это проблема
  вывода, а не файла. Проверять через Node.js или `chcp 65001`.
- В `devices.db` встречались дубли `_id` (например, `d0926` двумя строками с
  разными именами в снимке от 18.11; после обновления службой дубли исчезли).
  Всегда дедуплицировать по `_id`, не рассчитывая на уникальность строк.
- `miss: 1` в индексах встречается у штатных сущностей; не считать признаком
  ошибки без дополнительной проверки.

## Новые сущности: файл + запись в журнале

Проект видит сущность только если есть **оба**:

1. файл `jbase\<тип>\<id>.json`;
2. запись `<id>` в парном журнале (`visconts.db`, `layouts.db`, `vistemplates.db`,
   `dialogs.db`).

Запись индекса:

```json
{"_id":"vc096","parent":"vcg005","order":1000,"name":"Параметры"}
```

`parent` — группа-папка дерева, `order` — порядок внутри группы, `folder: 1` —
признак папки. Если файл добавили, а запись нет — объекта не будет в дереве
админки и в привязках.

## Права на запись

- Документы `jbase\{container,layout,template,dialog}\*.json` и `images\*` —
  обычные файлы, пишутся без повышения прав.
- `jbase\*.db` на рабочих стендах часто доступны только на чтение. Запись —
  отдельным node-скриптом, запущенным с повышением прав (UAC), и только если
  пользователь это разрешил:

```powershell
$node = (Get-Command node).Source
$p = Start-Process -FilePath $node -ArgumentList ('"' + $script + '"') `
     -WorkingDirectory (Get-Location).Path -Verb RunAs -WindowStyle Hidden -Wait -PassThru
"exit=$($p.ExitCode)"
```

  Скрипт должен быть идемпотентным (не дописывать запись, если `_id` уже есть) и
  печатать, что именно добавлено; код возврата проверять.

## Дозапись журналов (JSONL)

- Новые записи — только в конец файла; для каждого `_id` действует последняя.
- Приложение периодически **уплотняет** журнал (перезаписывает его целиком),
  поэтому дозапись при работающей службе может быть потеряна: сначала
  согласовать с пользователем, затем перечитать файл и убедиться, что запись
  последняя.
- Индексы (`visconts.db`, `locals.db`, `layouts.db`, `images.db`) служба обычно
  не перезаписывает, а живые данные (`devices.db`, `devcurrent.db`, `alerts.db`)
  — перезаписывает постоянно; их правка на работающей службе бессмысленна.
- Читать журналы построчно и пропускать битые строки: файл могут дописывать
  параллельно.
