# Регламент работы и ограничения среды

## Порядок выдачи изменений

1. **Снять исходное состояние.** Скопировать живой файл в `bak/` с датой и
   временем, посчитать SHA256.
2. **Собрать новую версию** отдельным файлом:
   `bak\<сущность>.patched-<что>-<YYYYMMDD>.json`.
3. **Проверить** (`validate-container.js`), собрать превью
   (`container-preview.js`), при необходимости PNG.
4. **Вернуть живой файл** в исходное состояние, если он правился для
   экспериментов; сверить SHA256 с исходным.
5. **Отдать пользователю**:
   - новый файл;
   - файл откатa;
   - превью;
   - короткое описание изменений (что добавлено, сколько, где);
   - инструкцию по применению и откату;
   - предупреждение, что без перезапуска проекта UI покажет старую версию.

Если пользователь прямо разрешил править живой файл (в некоторых проектах это
обычный режим работы), шаги 2–4 заменяются на: бэкап → правка живого файла →
проверка → сверка результата. Файл откатa и SHA256 обязательны и в этом случае.
Решение принимает пользователь: без разрешения — только отдельный файл.

Пример сообщения:

```text
Готово. Файлы в bak/:
- vc096.patched-dg172-20261118.json — новая версия
- vc096-before-dg172-20261117-141232.json — откат
- vc096-preview-dg172-20261118.png — превью 1:1

Применение: остановить службу → скопировать patched в
jbase\container\vc096.json → запустить службу.
Откат: вернуть before на место vc096.json.
Живой файл сейчас не изменён (SHA256 совпадает с исходным).
```

## Именование файлов

```text
<id>.patched-<тема>-<YYYYMMDD>.json      новая версия
<id>-before-<тема>-<YYYYMMDD-HHMMSS>.json  состояние до правки
<id>-preview-<тема>-<YYYYMMDD>.png         превью
```

Дата в имени — обязательна: в `bak/` накапливаются версии, и по имени должно
быть понятно, что за чем.

## Бэкап и сверка

```powershell
$root = "C:\ProgramData\IntraSCADA\intrascada\projects\<PROJECT>"
$live = "$root\jbase\container\vc096.json"
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
Copy-Item $live "$root\bak\vc096-before-$stamp.json"
(Get-FileHash $live -Algorithm SHA256).Hash
```

Перед выдачей убедиться, что живой файл побайтово равен исходному:

```powershell
(Get-FileHash $live -Algorithm SHA256).Hash -eq (Get-FileHash "$root\bak\vc096-before-....json" -Algorithm SHA256).Hash
```

## Что нельзя делать

- Перезапускать службу IntraSCADA, останавливать/запускать Windows-службы.
- Менять сетевые настройки, брандмауэр, реестр.
- Править `jbase\*.db` на работающей службе (она их перезаписывает).
- Править живые документы `jbase\...\*.json` без явного разрешения пользователя.
- Включать/выключать опрос устройств, менять каналы и адреса.
- Писать пароли и токены в файлы проекта, логи, превью и в скилл.
- «Тихо» исправлять чужие привязки и удалять непонятные элементы.

## Ограничения конкретной среды

Среда у каждого проекта своя — проверять, а не предполагать:

- какие плагины установлены: `<установка>\assets\plugins\`, `plugins\*.ihpack`,
  строка `Plugin ... loaded` в логе;
- какие каналы и устройства реально настроены: `units.db`, `devices.db`;
- используется ли `restapi` и внешние интеграции;
- есть ли связь с оборудованием: без неё реальные значения устройств
  недоступны, проверять поведение можно по файлам, превью и веб-клиенту;
- права на запись в каталог проекта: при отказе сообщить пользователю и не
  повышать права самостоятельно.

## Логи

```text
C:\Program Files\IntraSCADA\log\ih.log
```

Полезные строки:

```text
INFO: Project folder: ...\projects\<PROJECT>
INFO: Device engine has started, devices: <N>
```

По ним определяется, когда служба загрузила проект. Если правка файла сделана
позже — она ещё не применена.

## Исторические расхождения (не исправлять молча)

В рабочих проектах встречаются плитки, у которых клик открывает диалог другого
устройства (`lval` не совпадает с `masterLink.id`), «сдвинутые» координаты и
другие следы прошлых правок. Такие расхождения **перечислять списком**, но не
менять без явного разрешения: они могут быть частью исторической конфигурации
или чужой незавершённой работы.

## Гигиена работы

- Черновики, генераторы и превью — в `%TEMP%`, а не в проекте.
- Временные копии живых файлов удалять после сверки.
- Не оставлять в проекте файлы с паролями и отладочными скриптами.
- После работы перечислить, какие файлы созданы и какие изменены.
