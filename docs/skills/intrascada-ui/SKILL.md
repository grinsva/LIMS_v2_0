# IntraScada UI

Скилл для интерфейса IntraSCADA: файлы проекта на диске, форматы визуальных
сущностей, устройства и тревоги, веб-клиент и безопасный порядок выдачи
изменений. Работает в любом проекте IntraSCADA — конкретные имена и ID всегда
берутся из проекта, а не из примеров.

## Жёсткие правила

1. Не перезапускать службы IntraSCADA, не менять службы, сеть и реестр.
   Перезапуск делает владелец проекта.
2. По умолчанию изменения выдаются **отдельными файлами** (обычно в `bak/`
   проекта), а не прямой записью в живые `jbase\...\*.json`. Пользователь
   проверяет, внедряет и перезапускает сам. Прямая правка живого файла — только
   если он это явно разрешил; тогда сначала бэкап и SHA256.
3. Новую сущность проект видит, только если есть **и файл, и запись в парном
   журнале** (`visconts.db`, `layouts.db`, `vistemplates.db`, `dialogs.db`).
   Одно без другого не работает.
4. `*.db` — живые данные: служба их кэширует и перезаписывает. Читать можно,
   менять — только по согласованию; оперативные (`devices.db`, `devcurrent.db`,
   `alerts.db`) на работающей службе править бессмысленно.
5. Пароль администратора не хранить в скилле, документах и файлах проекта.
   Спрашивать у пользователя.
6. Не подключаться к ПЛК/устройствам, не включать опрос, не менять каналы
   связи. Не выполнять команды управления оборудованием ради проверки UI.
7. Секреты, токены и логи в репозиторий не добавлять.

## Быстрый старт

```text
проект:   C:\ProgramData\IntraSCADA\intrascada\projects\<PROJECT>
сущности: <проект>\jbase\{container,layout,template,dialog}\<id>.json
данные:   <проект>\jbase\*.db          (JSON Lines, UTF-8)
картинки: <проект>\images\             + jbase\images.db
логи:     C:\Program Files\IntraSCADA\log\ih.log
клиент:   http://localhost:8088/l<layout-id>   (админка: /admin/)
```

Проверить контейнер и увидеть раскладку без запуска приложения:

```bash
node scripts/validate-container.js "<путь>\<id>.json" --project "<проект>"
node scripts/validate-container.js "<путь>\<id>.json" --project "<проект>" --strict
node scripts/container-preview.js "<путь>\<id>.json" --project "<проект>" --out preview.html
```

`--strict` — для выпускаемой версии: любое предупреждение считается провалом.
Известные старые дефекты исключаются `--ignore "<текст>"`.

Найти устройства папки (например, все тревоги `dg172`):

```bash
node scripts/list-devices.js --project "<проект>" --folder dg172
```

## Сценарий: изменить существующий экран

1. Найти сущность: `jbase\layout\` → раскладка, `jbase\container\` → контейнер.
   Если известен только экран, искать по `"title"`/`"name"` в журналах
   (`layouts.db`, `visconts.db`).
2. Проверить, откуда берётся контейнер: статический фрейм (`widgetlinks.link.id`),
   подмена по локальной переменной (`link.did`/`link.prop` + `value.func`) или
   `dialog_any`. От этого зависит, какой файл править.
3. Сделать копию в `bak\` с датой и временем, посчитать SHA256.
4. Править **копию**, не живой файл (если пользователь не разрешил иное).
   Сохранять структуру и порядок полей соседних элементов.
5. Прогнать проверки: JSON, `list` ↔ `elements`, геометрия, привязки,
   `validate-container.js --strict`. Для раскладки — `container-preview.js`
   и просмотр превью.
6. Отдать: новый файл, файл откатa, превью, короткое описание, SHA256,
   инструкцию «остановить → скопировать → запустить» и предупреждение, что без
   перезапуска UI покажет старую версию.

## Сценарий: добавить плитки тревог в контейнер

1. Прочитать контейнер и определить образец плитки: `type: "template"`,
   `templateId` DI- или AI-шаблона, клик — `dialog_any`.
2. Получить список устройств: `scripts/list-devices.js --folder <dgXXX>`.
   Уникальность проверять по `_id`: в `devices.db` бывают дубли строк.
3. Для каждой плитки скопировать образец (deep copy), задать `_label`, `x/y`,
   `masterLink.id/title/title2`, `actions.action_1.left[0].value` →
   `targetFrameTable[0].lval` = id устройства.
4. Заголовок: `dn + " \u25AA\uFE0E " + name`; `title2` = `dn`.
   Имя на экране берётся из устройства, а не из `masterLink.title`.
5. Разложить по сетке, добавить заголовки-`text` и подложки-`rectangle`.
6. Прогнать `validate-container.js` (границы, пересечения, дубли, `lval`),
   собрать превью `container-preview.js`, при необходимости — PNG.
7. Положить в `bak/`: новый файл, файл откатa, превью, короткое описание,
   SHA256. Живой файл не трогать.

## Сценарий: переключение контейнера по кнопке

1. Локальная переменная в `locals.db`: `localNNN`, `name`, `defval` (строка).
2. У фрейма раскладки — `widgetlinks.link` с `enabled: true`, `did`, `prop`,
   `value.func` (`return inData;` или любая логика).
3. У кнопки — действие `setval_any` с `did`/`prop`, `local: true`,
   `value.func: "return 'vcNNN';"`.
4. Целевой контейнер — файл **и** запись в `visconts.db`.
5. Проверить в клиенте: клик меняет контейнер без перезагрузки страницы.

## Перед выдачей результата

- [ ] Новый файл — валидный JSON, одна строка, UTF-8 без BOM.
- [ ] `list` и `elements` согласованы, имена уникальны.
- [ ] Все элементы внутри `settings.w/h`, без наложений плиток.
- [ ] `--strict` пройден; оставшиеся предупреждения перечислены и объяснены.
- [ ] Каждое устройство встречается один раз, `lval == masterLink.id`.
- [ ] Все `did`/`prop`/`link.id`/`templateId`/`img.value` существуют.
- [ ] Для новой сущности есть запись в журнале с правильным `parent`.
- [ ] Старые элементы сохранены (diff по `_label`/id устройства).
- [ ] Есть файл откатa и инструкция по применению/откату.
- [ ] Пользователю сказано про перезапуск проекта.

## Что не делать молча

- Не «исправлять» чужие привязки диалогов, даже если они выглядят ошибкой:
  сообщить и оставить решение пользователю.
- Не менять `masterLink` у существующих плиток «для единообразия».
- Не удалять элементы, назначение которых непонятно.
- Не сохранять проект через веб-админку, если достаточно файла.
- Не считать `ERRAUTH` или `200 text/html` на месте картинки нормой: первое —
  отсутствие заголовка авторизации у ручного `fetch`, второе — отсутствующий
  файл.
