ЧТО ИМЕННО ДОБАВЛЕНО И ЧТО ОНО ДЕЛАЕТ
-------------------------------------
db\schema.sql
  Текстовый снимок структуры живой базы: таблицы, индексы, триггеры,
  представления. Только структура, без данных.
  Зачем: hist.db — бинарный файл, git показывает от него только
  "Bin 135168 -> 135168 bytes". Через schema.sql изменения структуры видно
  текстом, в том числе в VS Code.
  Приложение этот файл НЕ читает и НЕ использует. Это документация/история.

db\dump-schema.cjs
  Скрипт-генератор для schema.sql.
  node db\dump-schema.cjs          -> пересобрать schema.sql из живой базы
  node db\dump-schema.cjs --check  -> проверить, не устарел ли schema.sql
                                      (0 = всё совпадает, 1 = расхождение)
  Базу только читает, испортить не может.

db\verify-migrations.cjs
  Проверка "миграции = реальная структура".
  Создаёт пустую базу в памяти, применяет к ней все db\migrations\*.sql по
  порядку и сравнивает результат с живой базой.
  0 = цепочка миграций собирает ровно то, что в базе; 1 = расхождение.

db\migrations\0001_init.sql
  Базовая схема "как было до 16.11.2026". Заморожена, не меняется.
  Нужна как точка отсчёта для сборки базы с нуля.

db\migrations\0002_add_vk_shipment_id_prod_item.sql
  Сегодняшнее изменение: vk_shipment.id_prod_item (внешний ключ на
  vk_prod_item) + дополненный триггер trg_vk_shipment_dtlu.
  Уже применена к живой базе; файл нужен, чтобы повторить это на другой копии.

db\README.md, db\migrations\README.md
  Подробная документация: устройство, правила, шаблоны, ограничения.


ЧТО ПРОИСХОДИТ САМО
-------------------
- SQLite и приложение работают с db\sqliteDb\hist.db как обычно. Ничего
  менять в этом процессе не нужно.
- Рядом с базой появляются hist.db-wal и hist.db-shm (режим WAL) — это
  нормально, они в .gitignore и в git не попадают.
- Приложение само обновляет dtc/dtlu (триггеры *_dtlu) при записи данных.
- Всё остальное — вручную.


ЧТО ДЕЛАТЬ, КОГДА МЕНЯЕТСЯ СТРУКТУРА БАЗЫ (4 шага)
--------------------------------------------------
1. Оформить изменение миграцией: новый файл
   db\migrations\000N_короткое_имя.sql
   (правила и шаблон — в db\migrations\README.md).
2. Пересобрать снимок:      node db\dump-schema.cjs
3. Проверить цепочку:       node db\verify-migrations.cjs   -> должно быть "ok"
4. Закоммитить вместе:      hist.db + schema.sql + новый файл миграции

Перед любым изменением живой базы — сделать копию файла базы.


ЧТО ДЕЛАТЬ ПЕРИОДИЧЕСКИ
-----------------------
Действие                                  Когда                    Время
----------------------------------------  -----------------------  -----
node db\dump-schema.cjs --check           раз в неделю/месяц,      5 сек
                                          и после ручных правок
node db\verify-migrations.cjs             после изменений схемы,   5 сек
                                          перед коммитом
Резервная копия hist.db                   перед правками базы      1 мин
Накат миграций на другую копию базы       при появлении такой      1 мин
                                          копии/на новой машине

Обязательных регулярных действий нет. --check полезен как аудит: он ловит
случай "в базе структуру поменяли, а schema.sql и миграцию не обновили".


ЧТО ДЕЛАТЬ, ЕСЛИ ПРОВЕРКА НЕ ПРОШЛА
-----------------------------------
dump-schema.cjs --check вернул 1 и пишет "только в базе" / "изменено":
  значит структуру поменяли в базе, а файл не обновили.
  -> node db\dump-schema.cjs   (пересобрать) и посмотреть дифф в VS Code.

verify-migrations.cjs вернул 1 и пишет "нет в миграциях":
  значит изменение не оформлено миграцией.
  -> написать файл db\migrations\000N_*.sql, повторить проверку.

Обе проверки возвращают 2 при технической ошибке (нет файла базы, ошибка SQL).


КАК НАКАТИТЬ МИГРАЦИИ НА ДРУГУЮ БАЗУ
------------------------------------
1. Копия файла базы (обязательно).
2. Применить по порядку, например через CLI SQLiteStudio:

   & "C:\Program Files\SQLiteStudio\sqlitestudiocli.exe" -e db\migrations\0001_init.sql "D:\path\hist.db"
   & "C:\Program Files\SQLiteStudio\sqlitestudiocli.exe" -e db\migrations\0002_add_vk_shipment_id_prod_item.sql "D:\path\hist.db"

3. Проверить: node db\verify-migrations.cjs "D:\path\hist.db"  -> "ok"

Миграции применяются ОДИН раз и по порядку номеров: в SQLite нет
"ADD COLUMN IF NOT EXISTS", повторный накат 0002 обнулит id_prod_item.


ЧЕГО СОЗНАТЕЛЬНО НЕТ (поэтому автоматики не ждите)
--------------------------------------------------
- Нет git-хука, который сам обновляет schema.sql перед коммитом.
- Нет таблицы-реестра применённых миграций и автонаката.
- Нет выгрузки справочных данных ("не задано" с id=0 и т.п.) — только структура.
- hist.db по-прежнему лежит в git, поэтому в диффе от него остаётся строка
  "Bin ... bytes"; читаемая история — только через schema.sql и миграции.

Если что-то из этого нужно — это отдельная небольшая задача.


ГРАБЛИ, О КОТОРЫХ СТОИТ ПОМНИТЬ
-------------------------------
- hist.db нельзя править текстовыми инструментами (блокнот, sed, git apply):
  формат бинарный, файл сломается. Только SQL.
- Если база занята (открыта SQLiteStudio или приложением), правка может
  получить "database is locked". Чтение при этом работает.
- Правки могут лежать в hist.db-wal, а не в самом hist.db, пока не сделан
  чекпоинт. Копируя базу "файлом", копируйте после PRAGMA wal_checkpoint
  или вместе с -wal/-shm.
- Таблицы records, timeline, customtable повреждены (database disk image is
  malformed) — было до этих изменений. Дампу структуры это не мешает, но
  выгрузка их данных работать не будет.
- Известная ошибка схемы: vk_zvk.status ссылается на zv_status(id_pk), а такого
  столбца нет (есть id). Поэтому PRAGMA foreign_key_check на этой базе падает.
- Скриптам нужен Node.js 22.5+ (встроенный модуль node:sqlite). Внешних
  зависимостей и npm install не требуется.

ИТОГ
----
Приложение и SQLite работают сами. Всё добавленное — ручные инструменты
контроля: они делают структуру видимой в git и проверяемой.
Ничего не сломается, если их не запускать; но тогда изменения схемы останутся
невидимыми в истории, а расхождения — незамеченными.
