# LIMS_v2.0 — правила работы агента

## 1. Работать только через папку проекта и её `.git`

Папка проекта (далее `PROJECT`):

```
C:\ProgramData\IntraSCADA\intrascada\projects\LIMS_v2_0
```

Репозиторий — `PROJECT\.git`. Это единственная рабочая копия проекта.

- Все файлы читать и изменять **внутри `PROJECT`**. Не создавать и не использовать
  git-worktree, клоны и копии проекта в других каталогах для правок.
- Git-команды выполнять в `PROJECT` — либо из неё, либо с `git -C "PROJECT" ...`.
  Не запускать git в worktree/копиях: они указывают на тот же репозиторий и путают
  историю и состояние рабочей копии.
- Если сессия началась в worktree или копии: перенести результат в `PROJECT`,
  сообщить пользователю, что перенесено, и только после подтверждения удалить
  лишний worktree (`git worktree remove`).
- Отчёт о сделанном строить по реальному состоянию `PROJECT`: перед ответом
  проверять `git -C "PROJECT" status --short`.
- Пользователь смотрит изменения в VS Code, открытом на `PROJECT`, поэтому все
  правки должны быть видны в `git status`/диффах именно этой папки.
- `git add`, `commit`, `reset`, `worktree`, любые действия, меняющие историю или
  состояние индекса — **только по прямой просьбе пользователя**.

## 2. База данных

- Живая база, с которой работает приложение: `PROJECT\db\sqliteDb\hist.db`.
- Правки только через SQL (транзакции), не текстовыми инструментами: `.db` — бинарный формат.
- Перед любой работой с базой читать `db/schema/AGENT-NOTES.md`: инструменты,
  шаблоны скриптов и разбор уже случавшихся ошибок.
- Резервная копия живой базы — через backup API SQLite, а не копированием файла:
  часть изменений лежит в `hist.db-wal`. `Connection.backup(target)` копирует
  **из себя в target** — направление проверять до запуска.
- Системные таблицы `customtable`, `formulas`, `records`, `strrecords`, `timeline`
  **не проверять и не редактировать**:
  - не читать их структуру и содержимое, не включать в диагностику, отчёты и выборки;
  - не выполнять по ним `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `ALTER`, `DROP` —
    ни напрямую, ни через миграции и скрипты.
  - Исключение — только явная просьба пользователя, прямо касающаяся этих таблиц.
- Порядок изменения структуры:
  1. миграция `db/schema/NNNN_краткое_имя.sql`;
  2. `node db/schema/dump-schema.cjs` — обновить `db/schema/schema.sql`;
  3. `node db/schema/verify-migrations.cjs` — должно быть `ok`;
  4. `node db/schema/dump-schema.cjs --check` — код возврата `0`.
- После правки — `PRAGMA wal_checkpoint(TRUNCATE)`, иначе изменения останутся
  в `hist.db-wal` и не попадут ни в `hist.db`, ни в `git status`.
- Результат проверять скриптами проекта (`dump-schema.cjs`,
  `verify-migrations.cjs`), а не своим кодом.
- Схемные текстовые артефакты (`db/schema/schema.sql`, `db/schema/*`) коммитятся
  вместе с изменённой базой.
- Подробности: `db/schema/README.md` и `db/schema/MIGRATIONS.md`.

## 3. Файлы правил и копия в `AGENTS_README`

- При любом изменении правил в `AGENTS.md` сразу же обновлять `AGENTS_README`
  в той же папке: записывать туда **все актуальные правила целиком** на момент
  последнего изменения, а не только само дополнение.
- `AGENTS_README` — справка для человека: назначение файла правил, полный текст
  действующих правил и дата последней синхронизации с `AGENTS.md`.
- Правка правил считается сделанной, только когда `AGENTS_README` приведён
  в соответствие; в отчёте указывать, что копия обновлена.
- Правила синхронизировать во всех копиях проекта, где есть `AGENTS.md`
  (worktree, копии папки), чтобы расхождений не было.

## 4. UI в `jbase`

- Всё про интерфейс IntraSCADA — экраны (`layout`), контейнеры (`viscont`),
  диалоги, локальные переменные клиента, картинки, кнопки/действия, рантайм
  клиента, файлы `jbase/*.json`, журналы `jbase/*.db`, `images/*` — в скилле
  `intrascada-ui` («IntraScada UI»). Он установлен глобально
  (`%USERPROFILE%\.config\opencode\skills\intrascada-ui\SKILL.md` со справочниками
  `references/` и скриптами `scripts/`) и работает в любом проекте IntraSCADA;
  мастер-копия — `docs/skills/intrascada-ui/`.
- Перед правкой этих файлов загружать скилл `intrascada-ui`. Без запроса по этой
  области его не читать: подробности не должны попадать в контекст каждой сессии.
- Проектные детали этой установки — скилл `lims-jbase-ui`
  (`.opencode/skills/lims-jbase-ui/SKILL.md`): в списке не показывается, грузится
  по ID.
- В `AGENTS.md` эти подробности не дублировать — здесь только ссылки.
